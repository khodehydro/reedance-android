# تحویل معماری بدون رمز عبور — Windows Studio ↔ Reedance Android

**وضعیت: معماری هدفِ بدون رمز؛ یکپارچه‌سازی تولید هنوز مسدود به provision کلیدها و pin کردن امضاست.** این سند، مرجع اجرایی برای ایجنت Windows Studio و ایجنت Android است. در تعارض با جریان قدیمیِ واردکردن رمز فایل، این سند مقدم است.

## نتیجهٔ بررسی شاخهٔ Windows Studio

شاخهٔ ارسالی [`arena/132cfe2a-reedance-desktop`](https://github.com/khodehydro/reedance-desktop/tree/arena%2F132cfe2a-reedance-desktop) واقعاً جریان «بدون رمز فایل» دارد. بررسی این snapshot (`6707874`) نشان داد که `.rdpack` از هدر v1، AES-256-GCM، AAD و nonce تصادفی استفاده می‌کند و manifest از Ed25519 استفاده می‌کند. `npm test` با ۴۷ تست موفق و `npm run typecheck` موفق بود. این بررسی، ساخت نصاب Windows را تأیید نمی‌کند.

**قالب فایل با قرارداد v1 هم‌خوان است، اما اتصال end-to-end هنوز آمادهٔ انتشار نیست:**

1. Windows برای یک نصب تازهٔ Studio، کلید امضای Ed25519 تصادفی با شناسه‌ای مثل `sig-studio-…` می‌سازد. Android فقط امضاهایی را می‌پذیرد که کلید عمومی‌شان از قبل در `pack_distribution.json` برنامه pin شده باشد؛ کلید عمومیِ همراه خود manifest قابل‌اعتماد نیست. فعلاً مسیر روشن/قابل‌اعتماد برای export و pin کردن کلید عمومی Windows در UI/اپ Android وجود ندارد. باید یک کلید ناشر پایدار از مالک provision شود، کلید عمومی آن به Android pin شود و Studio همان کلید خصوصی را به‌کار ببرد؛ یا راهکار key rotation/pinning دیگری با هر دو ایجنت تصویب شود.
2. کلید AES واقعی `enc-main` باید در build Windows و Android یکی باشد. هر دو سمت اکنون fallback تستی عمومی دارند، ولی این کلید فقط برای تست است. کلید تولید هنوز به Android provision نشده؛ تا آن زمان خروجی production قابل‌گشودن/قابل‌اعتماد نیست.
3. فایل همراه قدیمی `Gülüm II` از دارایی‌های APK حذف شده است. برای آزمون debug فعلی، Android لینک GitHub را مستقیماً می‌گیرد و اندازه، SHA-256 و تگ GCM را بررسی می‌کند؛ هیچ فایل `.rdpack` آهنگ داخل APK نیست. این مسیر آزمونی عمداً manifest امضاشده ندارد و در release غیرفعال است.
4. فایل واقعی `pack_distribution.json` عمداً از Git مستثناست. بدون آن، allowlist میزبان، URLها و کلیدهای عمومی ناشر در APK تنظیم نشده‌اند؛ دانلود شبکه هنوز پیکربندی production ندارد.

ایجنت‌ها نباید صرفاً به‌خاطر اینکه تست‌های محلی exporter موفق‌اند، سازگاری production یا اعتماد به manifest را اعلام کنند. ابتدا هماهنگی کلیدهای بالا را حل و یک تست مشترک واقعی اجرا کنید.

## تصمیم اصلی

- Windows Studio یک فایل نسخه‌دار و رمزنگاری‌شده با پسوند `.rdpack` تولید می‌کند.
- اپ Reedance فایل را خودش دریافت/باز می‌کند، اصالت و سلامت آن را بررسی می‌کند و محتوایش را استخراج می‌کند.
- **هیچ رمز یا پسوردی از کاربر پرسیده، ساخته، وارد، ذخیره یا بین دو برنامه کپی نمی‌شود.** نه در Windows Studio و نه در Android.
- Android نباید برای دانلود یا بازکردن آهنگ به Profile، `PackPassword`, `PackKeyStore`, PBKDF2 یا «رمز فایل» نیاز داشته باشد. در شاخهٔ Android فعلی، جریان password-based و import محلی حذف شده‌اند؛ برای سازگاری با شاخه‌های قدیمی یا انتشار باید همین قرارداد بدون رمز حفظ شود.
- `.rdpack` نسخهٔ ۱ را از نو اختراع نکنید. از قالب و اعتبارسنجی مشترک همین مخزن استفاده کنید: [`PACKAGE_V1.md`](../reference/PACKAGE_V1.md) و schemaها/fixtureهای [`contracts/v1`](../../contracts/v1/).

## خروجی‌ای که Windows Studio باید بسازد

برای هر نسخهٔ آهنگ، خروجی‌ها عبارت‌اند از:

1. **`vNNNNNN-<sha256>.rdpack`** — محتوای نهایی شامل `lesson.json`، یک فایل صوتی و کاور اختیاری در یک ZIP؛ سپس ZIP با **AES-256-GCM** رمزنگاری می‌شود. قالب باینری، ترتیب فیلدها، nonce تازه، AAD، tag، حدود اندازه و نام فایل باید دقیقاً مطابق بخش ۳ `PACKAGE_V1.md` باشد.
2. **`latest.json`** — manifest امضاشدهٔ Ed25519 مطابق همان قرارداد؛ payload باید `songId`، زبان، نسخه، نام فایل، اندازهٔ واقعی، SHA-256 و `encryptionKeyId` را معرفی کند. امضای manifest و کلید عمومی پین‌شده در Android برای اعتبار ناشر/به‌روزرسانی هستند؛ رمزنگاری فایل جای امضای ناشر را نمی‌گیرد.
3. اطلاعات لازم برای انتشار، از جمله مسیر ثابت HTTPS مربوط به manifest. فایل `.rdpack` نسخه‌دار immutable بماند؛ برای نسخهٔ تازه، فایل جدید و `latest.json` تازه تولید شود.

### کلید رمزنگاری: هماهنگی لازم، بدون رمز کاربر

- خروجی باید از کلید توزیع AES-256 با شناسهٔ `enc-main` استفاده کند؛ **کلید داخل فایل و manifest قرار نمی‌گیرد**. nonce برای هر export با CSPRNG تازه و یکتا باشد.
- کلید بین exporter ویندوز و Android باید از قبل از سوی مالک پروژه/هماهنگی دو ایجنت provision شود. کلید واقعی را در Git، fixture عمومی، log، manifest، متن lesson، ایمیل عمومی یا گفتگو commit/paste نکنید؛ در صورت نبود کلید، فقط خروجی تستی با کلید تست مجاز بسازید و آن را برای انتشار معرفی نکنید.
- این handoff کلید واقعی یا روش تحویل امن آن را منتشر نمی‌کند. Android اکنون `REEDANCE_ENC_MAIN_KEY` را از Gradle property، environment یا `android/local.properties` می‌خواند؛ فقط debug بدون کلید محلی از کلید تستی عمومی استفاده می‌کند و build انتشار همچنان مسدود است. Windows باید همان شناسه و همان کلیدِ هماهنگ‌شده را به کار ببرد. **هیچ password-based KDF یا کلید تصادفیِ مستقل برای هر فایل** نسازید، مگر آن‌که قرارداد v2 جدیدی با Android توافق شود.
- نکتهٔ امنیتی: اگر کلید رمزگشایی در کلاینتی که کاربر دریافت می‌کند قابل‌دسترسی باشد، رمزنگاری به‌تنهایی DRM یا تضمین ریاضیِ «فقط همین اپ می‌تواند بخواند» نیست؛ هدف این قالب، انتقال و نگهداری امن‌تر، جلوگیری از ZIP خام و محدودکردن خواندن به جریان رسمی Reedance است. در UI یا مستندات، ادعای DRM قطعی نکنید.

## جریان هدف از ساخت تا پخش

```text
Windows Studio
  lesson نهایی + صوت انتخاب‌شده + کاور اختیاری
       → ZIP معتبر v1
       → AES-256-GCM با enc-main و nonce تازه
       → .rdpack نسخه‌دار + latest.json امضاشده
       → انتشار روی HTTPS

Reedance Android
  latest.json → بررسی امضای Ed25519/نسخه/شناسه
       → دانلود .rdpack → بررسی اندازه و SHA-256
       → رمزگشایی خودکار GCM با enc-main، بدون prompt رمز
       → فقط پس از تأیید tag، استخراج ZIP امن و اعتبارسنجی lesson/schema
       → ذخیره در فضای خصوصی اپ و پخش آفلاین
```

اگر در آینده آهنگ bundled شود، باید همین قالب و بررسی‌ها را داشته باشد؛ اما در وضعیت فعلی هیچ فایل آهنگ `.rdpack` داخل APK نیست. مسیر استثنایی debug برای لینک GitHub فقط اندازه، SHA-256 و GCM را بررسی می‌کند و جایگزین تأیید manifest ناشر برای انتشار نیست.

## الزامات محتوای داخل ZIP

- از [`lesson.schema.json`](../../contracts/v1/lesson.schema.json) و قواعد معنایی `PACKAGE_V1.md` پیروی کنید: شناسه/زبان پایدار، متن درس کامل، زمان‌بندی سطرها بعد از انتخاب و سینک صوت، `media.audio` با MIME/مدت/hash واقعی، و credits/حقوق واقعی.
- ZIP فقط ورودی‌های مجاز و نام‌های root را داشته باشد: `lesson.json`، دقیقاً یک `audio.mp3` یا `audio.m4a` یا `audio.wav`، و صفر یا یک `cover.jpg`/`cover.png`/`cover.webp`. مسیرهای traversal، symlink، فایل اجرایی، فایل اضافی، ورودی تکراری و ZIP رمزدار ممنوع‌اند.
- خروجی خام/ZIP باز یا کلید رمزگشایی را به‌عنوان فایل قابل انتشار تحویل ندهید؛ تنها `.rdpack` و manifest هستند.
- نسخه‌گذاری، سقف اندازه، hash، نام فایل و ساختار ZIP باید با schema/قرارداد Android هماهنگ باشد؛ خروجی نامعتبر را با اصلاح silent در سمت Android دور نزنید.

## چیزهایی که نباید در Windows Studio ساخته شوند

- صفحه یا دیالوگ «رمز فایل»، نمایش/تولید password اپراتور، ورود password در Android، مشتق‌سازی کلید با PBKDF2 از password یا ذخیرهٔ password.
- یک مسیر import محلی که از کاربر بخواهد `.rdpack` را انتخاب کند و برای آن رمز وارد کند؛ جریان نهایی، دانلود/بازکردن توسط خود Reedance است.
- ZIP بدون رمز به‌عنوان خروجی نهایی، encryption الگوریتمی متفاوت، nonce ثابت/تکراری، یا تغییر بی‌صدا در هدر RDPACK1.
- قراردادن کلید خصوصی Ed25519 در Android یا استفاده از test key برای انتشار.

## کار مورد انتظار از ایجنت‌ها

### Windows Studio

1. Exporter را دقیقاً مطابق `PACKAGE_V1.md` و این handoff بسازید؛ قرارداد `.rdpack` را تغییر ندهید.
2. تست golden مشترک اضافه کنید: byte-for-byte header، AES-GCM/AAD/tag، hash و طول manifest؛ تست decrypt باید با fixture Android اجرا شود.
3. تست منفی داشته باشید: کلید/شناسه ناشناخته، tag یا byte تغییریافته، اندازه/hash ناسازگار، ZIP نامعتبر و manifest امضانشده باید رد شوند.
4. هیچ secret واقعی را در شاخهٔ Windows یا pull request نگذارید. برای اجرای واقعی، درخواست provisioning را جداگانه و امن به مالک پروژه اعلام کنید.

### Android

1. جریان ورودی password-based (`PackPassword`, `PackKeyStore`, تنظیم رمز در Profile و import محلیِ رمزدار) حذف شده است؛ بازکردن فایل اکنون به ورودی کاربر وابسته نیست.
2. `PackDistributionKey` می‌خواند `enc-main` را از build config؛ debugِ بدون کلید از public test key مشترک با Windows استفاده می‌کند. کلید واقعی فقط از مسیر امن build (`REEDANCE_ENC_MAIN_KEY`) provision شود؛ در UI هیچ password prompt وجود ندارد.
3. حفظ شده است: بررسی امضای manifest، allowlist HTTPS، اندازه/hash، AES-GCM tag **پیش از استخراج**، ZIP امن، schema/semantic validation، ضد rollback، staging و فعال‌سازی اتمی. مسیر local file picker حذف شده است.
4. برای debug بدون کلید محلی، لینک آزمایشی `Gülüm 2` در `android/app/src/debug/assets/pack_direct_test.json` به `dl.reedance.ir` اشاره می‌کند؛ HTTP فقط برای همین مسیر debug و با اندازه/SHA-256 پین‌شده مجاز است. فایل از شبکه دانلود می‌شود و تا تأیید اندازه، SHA-256 و GCM هیچ ZIPی استخراج نمی‌شود. این مسیر فقط test key/debug است و manifest امضاشده را جایگزین نمی‌کند.
5. شبکهٔ production تا زمان افزودن کلید عمومی پایدار و URLهای مجاز به `pack_distribution.json` هنوز پیکربندی نشده است. خطاها باید علت واقعی (نسخه/امضا/خرابی/کلید ناشناخته/شبکه) را نشان دهند، نه «رمز اشتباه».

## معیار پذیرش مشترک

- یک `.rdpack` خروجی Windows با کلید تست، در تست Android بدون واردکردن هیچ password رمزگشایی و validate شود؛ Android نیز با همان fixture تست Windows را اجرا کند.
- نصب/دانلود موفق نیازمند ورود به Profile یا ذخیرهٔ رمز نباشد.
- فایل plaintext، tag خراب یا lesson نامعتبر هرگز استخراج/فعال نشود و نسخهٔ قبلی سالم بماند.
- package hash/size در manifest دقیقاً با artifact یکی باشد و `songId`, `targetLanguage`, `contentVersionCode`, schema و `encryptionKeyId` در تمام نقاط سازگار باشند.
- تست‌ها با کلیدهای تست انجام شوند؛ کلید واقعی خارج Git بماند.

## مرجع قدیمی

[`ANDROID_INSTALLER.md`](ANDROID_INSTALLER.md) تاریخچهٔ تصمیم password-based قبلی و وضعیت پیاده‌سازی فعلی را نگه می‌دارد؛ بخش‌های مربوط به password برای معماری هدف **منسوخ‌اند و نباید مبنای پیاده‌سازی Windows جدید قرار گیرند**. `PACKAGE_V1.md` همچنان مرجع هنجاری قالب v1 است، مگر آن‌که هر دو ایجنت با مالک پروژه قرارداد نسخهٔ جدیدی تصویب کنند.
