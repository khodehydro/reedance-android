# معماری انتشار Reedance — تصمیم نهایی و شرایط تحویل

**تصمیم معماری:** Windows Studio سازنده و ابزار کنترل کیفیت ناشر است؛ سرویس انتشار فقط فایل‌های امضاشده را میزبانی می‌کند؛ **Reedance Android تنها خوانندهٔ رسمی و تنها مقصد پخشِ فایل‌های تولیدی** است. فایل واسط یا رمز عبور به کاربر تحویل داده نمی‌شود. این تصمیم، مجوز انتشار APK/AAB نیست. قفل انتشار تا پاس‌شدن معیارهای پایین برقرار می‌ماند.

**نسخهٔ بررسی‌شده:** [شاخهٔ Windows Studio](https://github.com/khodehydro/reedance-desktop/tree/arena%2Fabbcc310-reedance-desktop)، commit `d5871574544100aa242a06f36695b57333aceea7`، Studio `1.0.6`. سمت Android بر مبنای `729365f` بررسی شد.

## ۱. نقش‌ها و مرز اعتماد

| جزء | وظیفه | آنچه نباید انجام دهد |
| --- | --- | --- |
| **Windows Studio (خصوصی و فقط برای ناشر)** | تدوین، همگام‌سازی و بررسی حق انتشار، ساخت `.rdpack` و `latest.json`، بازبینی داخلی خروجی و راستی‌آزمایی انتشار روی HTTPS | تبدیل‌شدن به پلیر عمومی یا توزیع درس خام برای کاربران؛ خروجی تست نباید منتشر شود |
| **میزبان HTTPS ناشر** | ارائهٔ بایت‌های رمزنگاری‌شدهٔ بسته و manifest امضاشده | تولید کلید، رمزگشایی بسته، تبدیل فرمت یا اعتمادسازی به‌جای امضای ناشر |
| **Reedance Android** | دریافت از ناشر مجاز، بررسی، نصب خصوصی و پخش آفلاین؛ کنترل دسترسی محصول جدا از اعتبار بسته | بازکردن فایل دلخواه از File Manager، دریافت رمز کاربر، قبول کلید عمومی ارائه‌شده توسط خود manifest یا ارجاع فایل به پخش‌کنندهٔ خارجی |

بازکردن آزمایشی خروجی در خود Studio، یک **کنترل کیفیت سمت ناشر** است، نه یک خوانندهٔ توزیع‌شده برای کاربر. Studio باید از کانال اپراتور جدا از برنامهٔ مصرف‌کننده توزیع شود. هیچ قرارداد `ACTION_VIEW`/ورود فایل، ابزار رمزگشایی عمومی یا خروجی plaintext در جریان مصرف‌کننده نباید اضافه شود.

### «فقط Android» به چه معناست؟

v1 فقط **خوانندهٔ رسمی** را محدود می‌کند؛ ZIP خام در اختیار کاربر نیست و برنامه‌ٔ عمومی بدون کلید فایل را باز نمی‌کند. ولی AES مشترک که برای رمزگشایی آفلاین در APK قرار می‌گیرد، در برابر مهندسی معکوس تضمین محرمانگی مطلق نمی‌دهد. Android Keystore یا مبهم‌سازی به‌تنهایی کلید مشترکِ تحویل‌شده با APK را به DRM تبدیل نمی‌کند. اعتماد به امضای Ed25519 و حق دسترسی اشتراک هم دو موضوع مستقل‌اند.

اگر شرط انتشار **رد هر خوانندهٔ غیرمجاز حتی پس از مهندسی معکوس APK** باشد، v1 قابل تصویب نیست. قبل از انتشار محتوای مشمول آن شرط، طراحی جداگانهٔ تحویل کلید/مجوز سمت سرور، کلیدهای دستگاه و مجوز آفلاین لازم است؛ حتی آن مدل هم ضبط صوت یا استخراج روی دستگاه کاملاً در اختیار مهاجم را مطلقاً ناممکن نمی‌کند. بدون تصمیم صریح دربارهٔ این شرط، از عبارت «DRM قطعی» استفاده نشود.

## ۲. قرارداد انتشار اولیه (`RDPACK1`)

1. **Windows** از خروجی نهایی درس، ZIP محدود و نسخه‌دار می‌سازد. پروفایل انتشار مشترک فعلی شامل `lesson.json`، یک صوت `audio.mp3|m4a|wav` و حداکثر یک کاور `cover.jpg|png|webp` است. خط‌های سینک‌شده، متن و ترجمه داخل lesson می‌مانند. محدودیت مشترک اندازه، نوع رسانه و مسیرها همان [قرارداد v1](../reference/PACKAGE_V1.md) و اعتبارسنج Android است. بستهٔ وابسته به قابلیت دیگری وارد کانال انتشار اولیه نمی‌شود.
2. ZIP با **AES-256-GCM**، شناسهٔ ثابت `enc-main` و nonce تازهٔ ۱۲ بایتی رمز می‌شود. کل هدر AAD است. خروجی `vNNNNNN-<sha256>.rdpack` به‌همراه `latest.json` امضاشدهٔ **Ed25519** تولید می‌شود. رمز فایل، KDF مبتنی بر رمز و کلید داخل manifest وجود ندارند.
3. ابتدا فایل نسخه‌دار روی HTTPS درج شود و نسخهٔ منتشرشده تغییر نکند. سپس `latest.json` همان آهنگ برای نسخهٔ جدید منتشر شود. نام فایل در manifest به همان پوشه/مبدأ resolve می‌شود. Studio می‌تواند پس از بارگیری و بررسی فایل‌های راه دور، انتشار را ثبت کند؛ صرف ایجاد فایل محلی انتشار نیست.
4. **Android** فقط manifest تعریف‌شده در تنظیمات توزیع و میزبان HTTPS مجاز را می‌پذیرد. به‌ترتیب: کنترل امضا با کلید عمومی پین‌شده؛ شناسهٔ آهنگ، زبان، نسخه و ضد rollback؛ اندازه و SHA-256؛ احراز تگ GCM **پیش از استخراج**؛ ZIP و schema و معنای درس؛ سازگاری رسانه؛ فعال‌سازی اتمی در فضای خصوصی برنامه. شکست هر مرحله نسخهٔ سالم قبلی را فعال نگه می‌دارد. پخش و سؤال‌های شنیداری از نسل نصب‌شده خوانده می‌شوند؛ فایل صوتی/بسته در APK قرار نمی‌گیرد.

### کلیدها و عملیات ناشر

- **امضا:** کلید خصوصی Ed25519 فقط در محیط کنترل‌شدهٔ ناشر باشد. ابتدا یک کلید ناشر پایدار و شناسهٔ آن تعیین شود؛ کلید امضای تصادفی هر نصب Studio را نباید خودکار trusted کرد. Android فقط شناسه و **کلید عمومی** خام ۳۲ بایتی متناظر را در `pack_distribution.json` pin می‌کند. کلید جدید باید پیش از استفاده در یک نسخهٔ Android منتشر شود؛ تا پایان مهاجرت، هم‌پوشانی اعتماد لازم است.
- **رمزنگاری v1:** Studio در زمان اجرا و Android در pipeline ساخت از `REEDANCE_ENC_MAIN_KEY` امن استفاده می‌کنند. یک مقدار ۳۲ بایتی مشترک تولیدی، به شکل متن base64url بدون padding، قالب مشترک پیشنهادی است. کلید در Git، فایل خروجی، manifest، نصاب Studio، لاگ یا گفتگو قرار نگیرد. **این کلید در build اندروید موجود و استخراج‌پذیر است**؛ با کلید خصوصی امضا اشتباه نشود. در v1 تغییر بی‌هشدار مقدار `enc-main` بسته‌های قبلی را می‌شکند؛ چرخش AES نیازمند برنامهٔ سازگاری و انتشار هماهنگ است.
- تولید باید fail-closed باشد: fallback عمومی و گزینه‌های خروجی آزمایشی تنها برای آزمون‌اند. نبود کلید یا پین، میزبان نامعتبر یا بستهٔ با کلید آزمایشی به معنی **عدم انتشار** است. path مستقیم debug جایگزین امضای تولید نیست.

## ۳. یافته‌های واقعی بررسی شاخهٔ Windows

| یافته | وضعیت و اقدام |
| --- | --- |
| ساخت بسته و manifest | `src/main/exporter.ts` AES-GCM/امضای Ed25519، نام‌گذاری نسخه‌دار، بازبینی داخلی و علامت‌گذاری کلید تست دارد. `src/main/publication.ts` انتشار را پس از دریافت HTTPS و بررسی امضا، شناسه/نسخه، هش و طول ثبت می‌کند؛ کلید تست از آن مسیر قابل انتشار نیست. |
| پینِ عملی ناشر | `src/main/keys.ts` provisioning/import و کلید امضای محلی را دارد. خروجی کلید عمومی خام قابل خواندن است، اما این معادل پین‌شدن در Android نیست. پیش از انتشار، تحویل امن **کلید عمومی و شناسهٔ دقیق** ناشر و آزمون نصب روی build مقصد لازم است. |
| ناسازگاری صوت داستان | این شاخهٔ Studio در صورت وجود `media.storyAudio`، فایل `story.mp3|m4a|wav` را واقعاً در ZIP می‌گذارد. Android فعلی این ورودی را در `StrictPackZip.kt` رد می‌کند و روایت داستان از TTS محلی استفاده می‌کند. **انتشار اولیه بدون صوت ضمیمهٔ داستان** است؛ متن داستان همچنان پشتیبانی می‌شود. قبل از انتشار بسته‌های دارای صوت داستان، schema مشترک، محدودیت‌های ZIP و اندازه، اعتبارسنجی رسانه، پخش Android و fixture بین‌پلتفرمی باید در یک تغییر هماهنگ پیاده و تأیید شوند؛ فایل را نباید صرفاً نادیده گرفت. |
| بررسی schema | `bootstrap-catalog`، `manifest-envelope` و `manifest-payload` بین snapshotهای بررسی‌شده یکسان‌اند. schemaهای lesson برای `storyAudio` یکسان نیستند؛ یکسانی رمزنگاری به معنی نصب‌شدن تمام خروجی‌های Studio نیست. |
| اشتراک | اعتبار ناشر یا موفقیت GCM به معنی داشتن Premium نیست. پرداخت، بازیابی اشتراک و entitlement واقعی باید در جریان جداگانه آزموده شوند. کانال عمومیِ HTTPS به‌تنهایی کنترل توزیع محتوای پولی نیست. |

## ۴. دروازهٔ انتشار و تحویل بین دو تیم

| مسئول | خروجی لازم پیش از بازکردن قفل انتشار |
| --- | --- |
| **مالک/ناشر** | دامنه و URLهای HTTPS تأییدشدهٔ `latest.json`، شناسه و کلید عمومی ناشر، provisioning امن AES، حقوق انتشار صوت/متن/تصویر، تصمیم دربارهٔ سطح حفاظت محتوای پولی و کلید امضای Android از مسیر امن. |
| **Windows Studio** | یک خروجی **تازه** در پروفایل مشترک بدون `storyAudio`، manifest و بستهٔ نسخه‌دار v1، و نسخهٔ دومِ همان آهنگ با شناسه‌های ثابت. برای interop غیرتولیدی فقط کلیدها/میزبان آزمایشی کنترل‌شده؛ برای rollout واقعی، فقط کلید ناشر تأییدشده. |
| **Android** | پین‌کردن دادهٔ ناشر، بررسی build/lint/tests، نصب و پخش واقعی روی API 26 و اندروید جدید، بررسی AAB امضاشده و عدم وجود fixture یا مسیر debug در release. قفل Gradle فقط پس از جایگزینی با اعتبارسنجی fail-closed و تأیید rollout باز شود. |
| **آزمون مشترک** | نصب v1 بدون رمز و پخش/تمرین شنیداری؛ به‌روزرسانی v1→v2 با حفظ تاریخچه، بوکمارک و لایتنر؛ قطع دانلود/کمبود فضا؛ امضای ناشناس، تگ/هش تغییرکرده، manifest قدیمی و ZIP نامعتبر؛ هیچ شکست نباید نسخهٔ قبلی را خراب کند. مصداق «v1→v2» در این ردیف نسخهٔ محتواست، نه تغییر container v1. |

**نتیجهٔ آزمون این بازبینی:** `npm test` شاخهٔ Windows: **۵۷/۵۷ موفق** (شامل آزمون‌های handoff/fixture و جریان Studio)؛ `npm run typecheck`: موفق. نصاب Windows ساخته/تأیید نشد. تولید واقعی کلید/پین، تست دانلود→نصب→پخش روی Android و انتشار اصلی انجام نشده‌اند. این سند معماری را تحویل می‌دهد، نه APK/AAB انتشار.
